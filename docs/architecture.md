# 아키텍처

## 한눈에 보기

```
 브라우저 A                         서버 (Go)                        브라우저 B
┌──────────────────┐          ┌──────────────────┐          ┌──────────────────┐
│ 보드 렌더러       │  click   │ 매칭             │  relay   │ 보드 렌더러       │
│   ↓ (row, col)   │ ───────▶ │ 순번 붙이기       │ ───────▶ │                  │
│ Web Worker       │          │ 행동 기록 (기보)  │          │ Web Worker       │
│  └ 게임 로직(JS) │ ◀─────── │ 해시 비교         │ ◀─────── │  └ 게임 로직(JS) │
└──────────────────┘  relay   │ 결과 기록         │  click   └──────────────────┘
                              └──────────────────┘
```

| 누가 | 하는 일 | 모르는 것 |
|---|---|---|
| **서버** | 매칭, 시드 발급, 행동에 순번 붙여 중계, 기록 저장, 해시·결과 대조 | 게임 규칙, 판의 상태 |
| **브라우저** | 보드 그리기, 클릭을 좌표로 변환, 게임 로직 실행 | — |
| **게임 로직** | 좌표를 받아 다음 상태 계산, 화면에 보일 것 설명 | 네트워크, 화면, 상대가 누구인지 |

## 락스텝(lockstep)

서버는 상태를 계산하지 않습니다. **같은 시작 상태(시드) + 같은 행동을 같은 순서로**
넣으면 양쪽 브라우저가 같은 결과를 얻는다는 점을 이용합니다.

- **차례 관리도 로직이 합니다.** 남의 차례에 온 클릭은 양쪽 로직에서 똑같이 무시되므로
  서버가 차례를 알 필요가 없습니다. "클릭 1번 = 턴 1번"이 아닌 게임(체스의 선택 → 이동,
  육목의 2개 놓기)도 그대로 됩니다.
- **불법 수도 로직이 거릅니다.** 조작된 클라이언트가 이상한 좌표를 보내도, 상대 브라우저의
  로직이 무시합니다.
- **대국 시계도 로직이 알려 줍니다.** 각 클라이언트가 해시와 함께 그 상태에서 누구 차례인지(`turn()`)를 보내고,
  서버는 먼저 온 보고로 시계를 넘깁니다. 양쪽 차례가 다르면 해시가 다른 것처럼 무효입니다.
  서버는 시간만 재고, 시간이 다 되면 상대를 승자로 정합니다.
- **무시된 행동은 해시로 압니다.** 행동 뒤의 상태 해시가 직전과 같으면 무시된 행동입니다.
  서버는 규칙을 몰라도 이것만으로 두 가지를 할 수 있습니다.
  - `maxActions`는 상태를 바꾼 행동만 셉니다. 무시된 클릭을 연타해서 강제로 무승부를 만들 수 없습니다.
  - 무시된 행동을 너무 많이 보낸 쪽은 패배 처리합니다 (`spam`). 기록이 끝없이 늘어나는 것도 막습니다.

### 이 구조에서 공짜로 얻는 것

`시드 + 행동 기록`만 있으면 판을 언제든 다시 만들 수 있습니다.

- **잠깐 끊김 복구**: 대국 중에 끊긴 플레이어를 15초 기다립니다. 돌아오면 시드와 지금까지의 기록을 보내고,
  그 클라이언트가 처음부터 재생해서 현재 판을 복원합니다. 새로고침도 같습니다.
- **기보 다시보기**: 끝난 대국마다 서버가 시드와 행동 기록을 파일로 남깁니다 (한 판에 1KB 안팎).
  다시보기 화면(`web/replay.html`)은 그걸 받아 게임 로직으로 한 수씩 다시 둡니다.
  기보에는 게임 코드 버전도 남깁니다. 제작자가 코드를 고쳐 버전이 바뀌었으면 다시보기 화면이 다르게 보일 수 있다고 알립니다.
  예전 코드를 보관해 그 코드로 재생하는 건 나중에 합니다.
- **관전**: 진행 중인 대국에 붙으면 끊겼다 돌아온 플레이어처럼 시드와 기록을 받아 재생하고, 그 뒤로는 양쪽과 같은 `relay`를 받습니다.
  락스텝이라 플레이어 브라우저에도 이미 판 전체가 있으므로, 관전 때문에 숨겨진 정보가 새로 새지는 않습니다.
- **결과 검증**: 서버가 같은 로직으로 기록을 재생하면 신고된 결과가 맞는지 확인할 수 있습니다 (예정).
  랭크전은 처음부터 서버 권위로 돌릴 계획이라, 락스텝 대국에는 붙이지 않을 수도 있습니다.

### 어긋남(desync) 감지

로직이 결정적이지 않으면(`Math.random()`, `Date.now()` 사용 등) 두 화면이 서로 다른
게임이 됩니다. 클라이언트는 행동을 적용할 때마다 상태 해시를 서버에 보내고, 서버는
같은 순번의 해시가 양쪽에서 다르면 대국을 무효 처리합니다.

### 결과 신뢰

승패는 각 클라이언트가 계산해서 보고합니다. 양쪽 보고가 같을 때만 기록하고,
다르면 분쟁으로 남깁니다. 랭킹이 생기면 서버 재생 검증을 붙입니다.

## 플랫폼이 할 수 없는 것

| 안 되는 것 | 이유 | 나중에 풀 방법 |
|---|---|---|
| 숨겨진 정보 (카드 패, 배틀쉽) | 양쪽 브라우저가 전체 상태를 가짐 | 서버가 로직을 실행 |
| 공정한 랜덤 (주사위) | 시드를 알면 다음 결과를 미리 계산 가능 | 서버가 그때그때 굴려서 중계 |
| 동시 행동 (가위바위보) | 먼저 낸 쪽의 선택이 보임 | 서버 보관, 커밋-공개 |
| 실시간 | 로직은 클릭 순서만 알고 시간은 모름 | 대국 시계는 플랫폼 기능으로 |
| 격자가 아닌 보드 (육각형, 선 그래프) | 렌더러가 격자만 그림 | — |

## 보안

업로드된 게임 코드는 남의 코드입니다.

- 브라우저: 사이트 화면(로비, 대전, 관전, 다시보기, 등록창)은 게임 코드를 직접 불러오지 않고 **게임 실행기**([web/engine.js](../web/engine.js))를 거칩니다.
  - 실행기는 `sandbox="allow-scripts"` iframe([web/runner/frame.html](../web/runner/frame.html)) 안에 게임마다 Worker를 하나씩 띄우고,
    판 상태는 그 Worker 안에만 둡니다. 화면은 "이 수를 둬라", "지금 판을 보여 달라"는 메시지로만 주고받습니다.
  - iframe은 출처가 없어서(opaque origin) 사이트의 쿠키, 저장소, 부모 화면에 손댈 수 없습니다.
  - 서버가 그 문서에 CSP를 붙입니다(`sandbox allow-scripts`, `connect-src 'none'`, `script-src`는 이 사이트만, eval 금지).
    그래서 `fetch`, 웹소켓, 다른 곳의 스크립트도 못 씁니다. 주소로 직접 열어도 같은 헤더로 갇힙니다.
  - 게임 함수 호출마다 시간 제한(기본 3초)이 있고, 넘으면 그 Worker를 끝냅니다. 무한 루프가 돌아도 사이트 화면은 멈추지 않습니다.
  - 돌아온 값(화면, 결과, 해시, 둘 수 있는 수)은 믿지 않고 모양과 크기를 검사해 알려진 칸만 씁니다.
  - Worker를 띄울 수 없는 브라우저에서는 iframe 안에서 바로 돌립니다. 격리는 같고, 무한 루프에 화면이 멈추는 것만 막지 못합니다.
  - 지금은 사이트와 같은 호스트에서 출처만 없앤 방식입니다. 나중에 실행기를 아예 다른 도메인에서 내보내면 한 겹 더 안전합니다.
  - 플레이그라운드(`npx boardmadang dev`)는 제작자가 자기 컴퓨터에서 자기 코드를 돌리는 도구라 페이지에서 바로 실행합니다.
- 서버(검증·AI 학습): 실행 시간 제한과 메모리 제한을 둡니다. 로직이 무한 루프를 돌 수 있고,
  이건 미리 검사할 방법이 없습니다(정지 문제).
- 대전 서버는 게임 로직을 실행하지 않으므로, 아무리 복잡한 게임이 올라와도 부담이 같습니다.
  악성 업로드가 비용을 일으킬 수 있는 곳은 AI 학습과 서버 측 검증뿐입니다.
  업로드 검사, 학습 예산, 제한값은 [abuse-and-limits.md](abuse-and-limits.md)에 정리했습니다.

## AI 학습 (예정)

이 플랫폼의 규칙은 그대로 강화학습 환경의 조건이 됩니다.

| 강화학습 | 플랫폼 |
|---|---|
| 관측 | `view()` / `observe()` → rows × cols × 채널 텐서 |
| 행동 | 클릭 좌표 `rows × cols` + 특수 행동 |
| 행동 마스크 | `legal()` |
| 보상 | 승 +1 / 패 −1 / 무 0 |
| 시뮬레이터 | 제작자의 `play()` |

### 학습 방식: AlphaZero 하나로 통일

신경망 + MCTS 자기대국(AlphaZero 방식)만 씁니다. PPO는 쓰지 않습니다.

- **PPO가 약한 이유**: 대국이 끝날 때의 승패 하나만 보상으로 받고, 수읽기를 하지 못합니다.
  바둑·체스처럼 수십~수백 수 뒤에 결과가 나고 전술 계산이 필요한 게임에서는 거의 늘지 않습니다.
  경우의 수 자체는 문제가 아닙니다. 신경망은 국면을 외우지 않고 패턴을 일반화합니다.
- **AlphaZero가 맞는 이유**: 매 수마다 MCTS 탐색 결과를 정답으로 배워서 학습 신호가 촘촘합니다.
  원래 같은 알고리즘·같은 설정으로 체스, 쇼기, 바둑을 학습시킨 범용 방식이라
  "게임마다 다른 알고리즘이 아니라 파이프라인 하나"라는 목표와 맞습니다.
- **필요한 조건은 이미 갖춰져 있습니다**: MCTS는 상태를 복사해서 "이 수를 두면?"을 미리 둬봐야 하는데,
  `play()`가 순수 함수이고 상태가 JSON이라 그대로 됩니다.

### 운영 원칙

- 신경망은 **완전 합성곱** 구조로, 보드 크기와 상관없이 같은 코드를 씁니다.
- 게임마다 학습합니다. 처음 보는 게임의 규칙은 판만 보고 알 수 없기 때문입니다.
- **학습은 예산제입니다.** "강해질 때까지"가 아니라 정해진 GPU 시간만큼만 돌립니다.
  큰 게임은 같은 비용으로 더 약한 AI가 나올 뿐 비용이 늘지 않습니다. → [abuse-and-limits.md](abuse-and-limits.md)
- **난이도**는 학습 체크포인트와 **MCTS 탐색 횟수(생각 시간)**로 조절합니다. 탐색 횟수만 바꿔도
  추가 학습 없이 여러 단계가 나옵니다.
- AI끼리 자기대국한 결과로 **밸런스 분석**(선공 승률 등)을 제작자에게 제공합니다.
  AI가 아주 강하지 않아도 의미 있는 숫자가 나옵니다.
- 국면 수가 작은 게임(틱택토 등)은 학습 대신 **완전 탐색**으로 풀어서 확정 결론을 줍니다.
  탐색할 국면 수에도 상한을 둡니다.
- **유명한 게임(바둑, 체스)은 기존 오픈소스 엔진**(KataGo, Stockfish 등)을 연결합니다.
  이미 사람보다 강하고, 19×19 바둑을 직접 학습시키는 건 비용상 불가능합니다. 연결할 때 각 엔진의 라이선스를 확인합니다.
  보드마당 학습 파이프라인의 진짜 가치는 **세상에 없던 창작 게임의 AI**입니다.
  창작 게임은 대부분 판이 작고 규칙이 단순해서 적은 예산으로도 쓸 만한 AI가 나옵니다.
